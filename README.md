# اسکیل طراحی و بهبود UI/UX محصول

تبدیل «رابط را بهتر کن» به مسئله مشخص، تحقیق مستند، طراحی قابل پیاده‌سازی و نتیجه قابل اندازه‌گیری. پیش‌فرض: وب فارسی و راست‌به‌چپ؛ زبان، برند و استک واقعی محصول بر این پیش‌فرض مقدم‌اند.

## شروع در Codex

اسکیل در [.agents/skills/product-ui-ux/SKILL.md](.agents/skills/product-ui-ux/SKILL.md) قرار دارد. این مخزن را باز کن، در صورت نیاز جلسه را دوباره باز کن و بنویس:

```text
$product-ui-ux
حالت: audit
محصول: [نام و لینک یا مسیر کد]
کاربر: [چه کسی؟]
کار اصلی: [چه کاری باید تمام شود؟]
مشکل: [کجا گیر می‌کند؟]
محدودیت: [زمان، برند، استک، دسترسی]
خروجی: ۵ مشکل اولویت‌دار با شواهد و پیشنهاد اجرایی
```

اگر اسکیل خودکار پیدا نشد، مسیر `SKILL.md` را صریحاً در درخواست بده. برای محصول دیگر، پوشه `product-ui-ux` و تمام زیرپوشه‌هایش را به `.agents/skills/` مخزن آن محصول کپی کن. این کار ابزار ثالثی نصب نمی‌کند.

## کارهایی که جلو می‌برد

| حالت | خروجی |
| --- | --- |
| `discover` | بریف، فرضیه‌ها، سؤالات تحقیق و مسیر اصلی |
| `research` | مقایسه الگوها با لینک، شواهد و محدودیت انتقال |
| `audit` | مشکلات P0 تا P3، شواهد و راه اصلاح |
| `system` | توکن‌های معنایی و قرارداد کامپوننت‌ها |
| `redesign` | حداکثر دو جهت طراحی و پیشنهاد منتخب |
| `implement` | تغییر کد متناسب با استک و بررسی رفتاری |
| `measure` | یک KPI اصلی، سنجه‌های محافظ و طرح رویدادها |
| `handoff` | وضعیت‌ها، معیار پذیرش و راهنمای تحویل |

این‌ها حالت‌های داخل اسکیل‌اند؛ فرمان نصب‌شده نیستند. طبیعی هم می‌شود درخواست داد: «مسیر ثبت‌نام را با همین اسکیل بررسی کن و سه مانع اصلی را اصلاح کن».

## چطور کمک دقیق‌تری بگیری؟

به‌جای «یه UI خفن بساز»، بگو «کاربر جدید باید اولین پروژه‌اش را در موبایل بسازد؛ الان در فرم مشخصات رها می‌کند؛ برند فعلی حفظ شود». اگر داده نداری، همان را بگو؛ اسکیل نتیجه تحقیق یا نرخ تبدیل جعل نمی‌کند.

1. یک کار مهم کاربر را انتخاب کنیم؛ مثلاً رسیدن از ثبت‌نام به اولین ارزش محصول.
2. وضعیت فعلی را با تصویر، مسیر کلیک و داده موجود ثبت کنیم.
3. حداکثر پنج مانع را با دلیل، راه‌حل و معیار پذیرش اولویت‌بندی کنیم.
4. یک برش کوچک را طراحی و پیاده کنیم؛ موبایل، خطا و حالت خالی را هم ببینیم.
5. با کاربران واقعی بررسی کنیم؛ آزمایش کمّی به داده و ترافیک مناسب نیاز دارد.
6. تصمیم‌های تأییدشده را در توکن‌ها و کامپوننت‌ها نگه داریم تا صفحه بعدی سریع‌تر ساخته شود.

## یادگیری از جونیور تا سینیور

| سطح بررسی | تمرکز | تمرین و معیار خروج |
| --- | --- | --- |
| پایه | سلسله‌مراتب، فاصله، تایپوگرافی فارسی | یک فرم با label، focus و خطای روشن |
| میانی | جریان، وضعیت‌ها و کامپوننت‌ها | مسیر کامل با loading، empty، error و success |
| پیشرفته | تحقیق، اولویت و سنجش | فرضیه قابل رد، تست کاربردپذیری و تعریف دقیق KPI |
| سینیور | تصمیم محصول و مقیاس سیستم | توضیح trade-off، هزینه نگهداری و نتیجه واقعی |

این سطح‌ها زاویه بررسی‌اند؛ ادعای تجربه انسانی یا جایگزین مصاحبه با کاربر نیستند. می‌توانی بگویی: «دلیل این تصمیم را مثل مربی توضیح بده و یک تمرین کوچک بده».

## اتوماسیون

قالب‌های [بریف](.agents/skills/product-ui-ux/templates/brief.md)، [گزارش بررسی](.agents/skills/product-ui-ux/templates/review.md)، [طرح تحقیق](.agents/skills/product-ui-ux/templates/research-plan.md)، [دیزاین سیستم](.agents/skills/product-ui-ux/templates/design-system.md) و [سنجش](.agents/skills/product-ui-ux/templates/measurement.md) خروجی‌ها را قابل تکرار می‌کنند. برای سه اسکرین‌شات و گزارش overflow، زبان، جهت صفحه و خطاهای JS:

```bash
# از ریشه مخزن؛ ابزار اختیاری تصویربرداری
python -m venv .venv
.venv/bin/python -m pip install -r requirements-browser.txt
.venv/bin/python -m playwright install chromium

# سرور محصول را با دستور خود همان محصول اجرا کن؛ سپس:
.venv/bin/python .agents/skills/product-ui-ux/scripts/capture_ui.py \
  --url http://127.0.0.1:3000 \
  --output artifacts/current
```

اگر Chromium سیستم نصب است، `--browser-path /usr/bin/chromium` بده؛ دانلود مرورگر لازم نیست. پوشه خروجی باید جدید باشد؛ فایل قبلی بازنویسی نمی‌شود. URL نمونه، لینک پیش‌نمایش محصول نیست.

ابزار لاگین یا کلیک نمی‌کند و گواهی دسترس‌پذیری صادر نمی‌کند. کنتراست، کیبورد، screen reader و انجام وظیفه بررسی جداگانه می‌خواهند. تصاویر ممکن است داده شخصی صفحه را داشته باشند؛ خروجی محلی و از Git مستثناست. خود صفحه ممکن است هنگام بازشدن analytics ارسال کند.

```bash
python -m unittest discover -s tests -v
```

آزمون مرورگر به Playwright و Chromium نیاز دارد؛ در نبود آن‌ها صریحاً skip می‌شود. آزمون‌ها فقط سرور محلی را باز می‌کنند.
